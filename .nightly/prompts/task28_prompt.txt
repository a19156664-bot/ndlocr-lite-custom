Task 28: [FIX] The first PDF page crashes, and so does any missing image

You MUST read AGENTS.md at the repository root and follow its rules.

The commander reproduced and diagnosed both problems. Do not re-investigate.
They are the SAME underlying defect, reached by two different routes.

================================================================================
1. WHAT HAPPENS
================================================================================
1.1 ROUTE A - EVERY PDF, ON ITS FIRST PAGE

Opening a folder that contains a PDF, or using the "Open PDF" button, crashes
immediately:

    _switch_image(doc_p0001.png)
       PNG exists at this point : False
       ocr_error : 'Error: Image not found at ...\\ndlocr_pdf_xxxx\\doc_p0001.png'
       container.content type   : Text
       image_control.page       : False
       AssertionError: Image Control must be added to the page first

PDF pages are rendered LAZILY: `plan_pdf_pages` only computes the PNG paths, and
`ensure_page_rendered` writes the file just before it is shown. That is correct
and must stay.

The bug is the ORDER inside `_switch_image`:

        if path not in self.image_states:
            self.image_states[path] = {
                ...
                "ocr_state": OcrState.IDLE if os.path.exists(path) else OcrState.ERROR,
                "ocr_error": None if os.path.exists(path) else f"Error: Image not found at {path}"
            }
        state = self.image_states[path]
        ...
        self.ocr_error = state["ocr_error"]          # already an error
        ...
        if path in self.pdf_page_map:
            ensure_page_rendered(path, pdf_path, page_index)   # NOW the file exists

The existence check runs BEFORE the page is rendered, so a perfectly good PDF
page is recorded as "image not found". Rendering then succeeds, but `ocr_error`
is never cleared.

1.2 ROUTE B - ANY MISSING IMAGE, NOTHING TO DO WITH PDFs

        _switch_image(<a path that does not exist>)
        AssertionError: Image Control must be added to the page first

So even the legitimate "this file is gone" case crashes instead of showing the
error. This is the deeper defect and it must be fixed too.

1.3 WHY IT CRASHES

When `self.ocr_error` is truthy, `_switch_image` does

        self.image_container.content = ft.Text(self.ocr_error, ...)

which REMOVES `self.stack` - and therefore `self.image_control` - from the
control tree. `image_control.page` becomes None. Immediately afterwards
`_switch_image` calls `self.update_layout(...)`, which reaches
`ImageViewer._update_viewer` in custom_gui/viewer.py:

        if self.page:                     # the VIEWER has a page, so this passes
            self.image_control.update()   # but image_control does NOT -> assert

Guarding on the parent's `page` does not prove the CHILD is attached.

1.4 THIS IS NOT NEW

The commander confirmed the same crash on master before Task 27, so it came in
with Task 26. It was missed at acceptance because the verification script had
already called `ensure_page_rendered` for that page, so the PNG existed and the
error branch was never taken. Assume nothing about existing behaviour being
"verified"; make the tests below prove it.

2. DEFINITION OF DONE
================================================================================
[A] Render before deciding whether the file exists.
    In `_switch_image`, a PDF-backed path must be rendered via
    `ensure_page_rendered` BEFORE any `os.path.exists(path)` test and BEFORE the
    entry in `self.image_states` is created. After a successful render the page
    must be treated as a perfectly normal existing image: `ocr_state` IDLE,
    `ocr_error` None, OCR started lazily as usual.

[B] A genuine render failure is still an error.
    If `ensure_page_rendered` raises, record the reason in `ocr_error`, show it,
    and keep the application usable. Do not crash.

[C] The error display must never crash. THIS IS THE PRIMARY DELIVERABLE.
    Whatever path sets `ocr_error` - a missing file, a corrupt image, a failed
    render - showing that error must not raise. Choose ONE of:
      (i)  make the update guards check the control that is about to be updated
           rather than the viewer, for example `if self.image_control.page:`
           inside `ImageViewer._update_viewer` in custom_gui/viewer.py. Only
           that guard may change in that file - the pure functions
           original_to_display / display_to_original / calculate_fit_scale /
           apply_pan / calculate_label_position and class InteractionMode MUST
           NOT change; or
      (ii) stop detaching the stack: keep `self.stack` as the container content
           and surface the error somewhere that does not remove the image
           control from the tree.
    State which you chose and why.

[D] Recovering from an error must work.
    After landing on a broken image and seeing the error, moving to a GOOD image
    must display it normally - the image control must be back on screen, zoom
    reset to fit, rectangles and highlights working. Going back to the broken one
    must show the error again, still without crashing. Repeat that cycle at least
    twice in your test.
