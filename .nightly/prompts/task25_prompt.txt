Task 25: [NEW] "Right-to-left" button - repair text from pre-war right-to-left horizontal writing

You MUST read AGENTS.md at the repository root and follow its rules.

--------------------------------------------------------------------------------
1. PURPOSE - THE REAL PROBLEM, WITH REAL DATA
--------------------------------------------------------------------------------
Japanese magazines from the early Showa era (1920s-1930s) print horizontal text
RIGHT TO LEFT. Modern OCR reads left to right, so every such line comes out
character-reversed. The OCR engine itself is not wrong - it simply has no way to
know the page's writing direction.

This is REAL OUTPUT from this application, verified by the human owner:

    Region 5:
        く近が嬢ヒツリトイデの染馴おんさ皆（合聯發ドツウリハ）
        。すで眞寫の中度支おるす演出に１風暴］書映トンウマラバ

Reversing each line character by character, AND flipping the direction of the
bracket characters, produces correct Japanese:

        （ハリウツド發聯合）皆さんお馴染のデイトリツヒ嬢が近く
        バラマウント映書［暴風１に出演するお支度中の寫眞です。

Note carefully what happens to the brackets. A naive character reversal alone
would leave them backwards:

        ）ハリウツド發聯合（      <- wrong, brackets inverted
        （ハリウツド發聯合）      <- correct, brackets also mirrored

The human owner has explicitly decided that brackets MUST be mirrored.

--------------------------------------------------------------------------------
2. THE SPECIFICATION - DECIDED BY THE HUMAN OWNER. DO NOT REDESIGN.
--------------------------------------------------------------------------------
2.1 The unit of conversion is ONE LINE.

    Text is split on newlines. Each line is reversed INDEPENDENTLY. The ORDER OF
    THE LINES DOES NOT CHANGE.

    This is the owner's requirement, stated as:
        "改行マークがあればそこまでを1文として右から変換をおこなってください"
        (if there is a newline, treat up to it as one sentence and convert that)

    Worked example given by the owner:

        input           1234567890
        output          0987654321

        input           1234567890
                        0987654321

        output          0987654321
                        1234567890

    WARNING: that second example is ambiguous on its own, because those two
    lines happen to be each other's reverse. Do NOT implement it as "reverse the
    order of the lines". It is "reverse the characters within each line, keeping
    the lines in their original order". Verify your understanding against this
    UNAMBIGUOUS case, which you must include as a test:

        input           ABC
                        123

        output          CBA
                        321

    (NOT "123 / ABC", which is what line-order reversal would give.)

2.2 Digits are reversed like any other character.
    The owner's own example requires 1234567890 -> 0987654321. Do not add
    special handling to keep numbers intact.

2.3 Brackets are mirrored.
    After reversing, every character that is one half of a directional pair must
    be replaced by its partner. At minimum handle these pairs, in BOTH
    directions:

        （ ）    (fullwidth parenthesis, U+FF08 / U+FF09)
        ( )      (ASCII parenthesis)
        「 」    (U+300C / U+300D)
        『 』    (U+300E / U+300F)
        【 】    (U+3010 / U+3011)
        ［ ］    (fullwidth square, U+FF3B / U+FF3D)
        [ ]      (ASCII square)
        ｛ ｝    (fullwidth brace, U+FF5B / U+FF5D)
        { }      (ASCII brace)
        〔 〕    (U+3014 / U+3015)
        〈 〉    (U+3008 / U+3009)
        《 》    (U+300A / U+300B)
        < >      (ASCII angle)
        ＜ ＞    (fullwidth angle, U+FF1C / U+FF1E)

    Define this as a single explicit mapping table in the code with a comment
    explaining why it exists. Do not try to derive it from unicodedata.

2.4 The operation must be its own inverse.
    Applying the conversion twice must return the ORIGINAL string exactly. This
    follows from the mapping being symmetric, and it means the button doubles as
    an undo. Assert it in a test.
