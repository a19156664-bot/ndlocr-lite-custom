1. DEFECT ONE - append_mark_line glues onto a file with no trailing newline
================================================================================
The current implementation opens the file in "a" mode and writes line + "\n".
If the file does not already end with a newline, the appended line is welded
onto the last line:

    file before:   既存行\t本文            (no trailing newline)
    append        "x.jpg\t【広告】"
    file after:    既存行\t本文x.jpg\t【広告】\n      <-- ONE corrupted line
    wanted:        既存行\t本文\nx.jpg\t【広告】\n

The commander reproduced this. It is not hypothetical: any TXT the user opens
in Notepad and saves can lose its final newline, and the next 広告 press then
destroys the line that was already there.

FIX

    Before appending, check whether the file exists and is non-empty and does
    NOT end with "\n". If so, write a "\n" first, then the line. An empty file
    and a missing file must NOT gain a leading blank line. A file that already
    ends with "\n" must not gain a second one.

    Keep everything else about the function identical: still utf-8, still
    returns False without writing when the exact line is already present, still
    returns True when it writes, still lets an OSError propagate.

WHY THE TEST DID NOT CATCH IT

    tests/test_page_marks.py DOES have a case named "File whose last line has
    no trailing newline". But it writes the file as

        txt_path.write_text("foo.jpg\t【広告】")

    and then appends THE SAME LINE, so the duplicate guard returns False and
    the append path is never executed. The test asserts False and passes,
    while proving nothing. This project has now shipped EIGHT tests that could
    not detect the bug they were written for.

    Repair that case so it appends a DIFFERENT line, and assert the exact full
    contents of the file afterwards with ==, not with `in`.

    Add a second case: a file that is completely empty (write_text("")), and a
    file that does not exist. Neither may produce a leading blank line.

2. DEFECT TWO - state["mark"] raises KeyError and breaks an existing test
================================================================================
In custom_gui/app.py, `_switch_image` reads

    self.mark = state["mark"]

A state dictionary that predates this feature has no "mark" key, so this
raises. It already breaks a test that was passing before Task 36:

    tests/test_ocr_scheduler.py::test_app_level_ocr_call_count
    KeyError: 'mark'    at custom_gui/app.py:651

Task 36 was told: "If an existing test fails, STOP and report which one and
what it expects." That did not happen.

FIX

    Read it defensively - `state.get("mark")` - so a state built without the
    key yields None, which is exactly what an unstamped page means.

    Do the same for `self.mark = self.image_states[image_src]["mark"]` in
    __init__ if it has the same problem. Check every place that indexes
    "mark" with [] and decide, for each, whether a missing key is possible.
    `self.image_states[self.image_src]["mark"] = mark_str` is an assignment
    and is fine as it is.

    Do NOT "fix" this by rewriting existing state dictionaries elsewhere, and
    do NOT edit tests/test_ocr_scheduler.py. The application must tolerate a
    dictionary without the key.

3. TEST REPAIR - test_h fails against CORRECT code
================================================================================
tests/test_mark_buttons.py::test_h_save_stamped_page_retains_mark fails today,
but the application is right and the test is wrong.

Pressing 広告 CREATES <image stem>.txt. So when the test then calls
`_start_export("current")`, Task 35's overwrite confirmation opens and nothing
is written - the file still holds only the mark line, so the assertion that
"Hello" is in it fails.

The commander drove this by hand: after pressing the 上書き保存 button, the
file correctly contained BOTH the mark line and the OCR text.

FIX

    After `app._start_export("current")`, assert that `app._save_dialog` is
    not None and its title is "上書き確認", find the action whose text is
    "上書き保存", and call its on_click. THEN read the file and assert both
    the mark line and the OCR text are present.

    Asserting that the dialog appeared is part of the test now - it documents
    the real behaviour, so do not skip it by deleting the file first or by
    exporting somewhere else.
