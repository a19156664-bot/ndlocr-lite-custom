================================================================================
1. THE CRASH
================================================================================
The user pans the image (Mode: PAN, dragging) and gets:

    File "custom_gui/app.py", line 813, in _on_pan_update
        self._update_viewer()
    File "custom_gui/app.py", line 1028, in _update_viewer
        self._update_selections_ui()
    File "custom_gui/app.py", line 1009, in _update_selections_ui
        _safe_update(self.rects_layer)
    File ".../flet/core/control.py", line 493, in build_update_commands
        assert self.__uid is not None
    AssertionError

After that first failure everything is broken - panning, region selection and
page turns all raise, because the Python control tree and the flet client are
now out of sync. Restarting the application recovers it.

================================================================================
2. ROOT CAUSE - CONFIRMED, NOT A GUESS
================================================================================
2.1 flet runs every non-async event handler on a THREAD POOL, unserialised.

    .venv/Lib/site-packages/flet/core/page.py, on_event_async:

        if asyncio.iscoroutinefunction(handler):
            await handler(ce)
        else:
            self.run_thread(handler, ce)      # <- ThreadPoolExecutor, no lock

    During a drag, on_pan_update fires dozens of times a second. Each firing is
    a SEPARATE thread pool task, and they overlap.

2.2 `_update_selections_ui` is not atomic.

    It clears three control lists and rebuilds them, then updates them:

        self.rects_layer.controls.clear()
        self.highlight_layer.controls.clear()
        self.selections_list.controls.clear()
        ... append many new controls ...
        _safe_update(self.highlight_layer)
        _safe_update(self.rects_layer)
        self.selections_list.update()

    Two overlapping pan events therefore clear and rebuild the SAME lists while
    both are inside page.update(). flet assigns control uids only after its
    send_commands round trip, so an interleaving leaves a control in the tree
    with __uid still None, and the next update asserts.

    page.update() holds a lock, but that lock only serialises update against
    update. It does not stop another thread mutating the tree mid-update.

2.3 Why it only appeared now.

    The race has existed since Task 04/05 (`git log -S "self._update_selections_ui()"`
    confirms). It was harmless because the rebuild was tiny:

        for line in filtered_lines:            # <- OCR lines inside the region
            highlight = ft.Container(...)
            self.highlight_layer.controls.append(highlight)

    Before pre-OCR, a freshly opened page had no results yet, so filtered_lines
    was empty and the critical section was a few microseconds. After Task 30's
    cache, EVERY page has its full OCR result the instant it is shown - 26 to
    144 lines in the user's material - so every single pan event now rebuilds
    dozens of controls. The window went from negligible to easy to hit.

    Task 30 is the trigger, not the cause. Do not "fix" the cache.

================================================================================
3. DELIVERABLES
================================================================================
[A] Stop rebuilding everything on every pan event. THIS IS THE MAIN FIX.

    In `_on_pan_update`, the PAN branch currently ends with

        self._update_viewer()
        self._update_selections_ui()

    Panning only changes self.offset_x / self.offset_y. The rectangles and the
    yellow highlights do not change shape - they only need to move by the same
    amount as the image.

    Preferred solution: move the layers instead of rebuilding their contents.
    `self.image_control` is already panned with `.left` / `.top`. Do the same
    for `self.highlight_layer` and `self.rects_layer` as whole controls, so a
    pan becomes a handful of attribute writes and one update, with NO control
    creation and NO list mutation.

    That means the children of those layers must be positioned WITHOUT the pan
    offset baked in, and the layer itself carries the offset. Keep using
    `original_to_display` from custom_gui/viewer.py - it takes offset_x and
    offset_y, so pass 0.0 for them when positioning children and put the offset
    on the layer. Do NOT modify custom_gui/viewer.py.

    If you cannot make that work correctly, the fallback is to keep rebuilding
    but do it at most once every 100 ms during a drag, with a final rebuild in
    `_on_pan_end`. Say clearly which one you implemented and why.

    Either way, `_on_pan_update` in PAN mode must no longer call
    `_update_selections_ui` on every event.

[B] Make `_update_selections_ui` atomic.

    Even with [A], other threads still call it: `_on_pan_end`, `_switch_image`,
    `delete_rect`, `_on_ocr_complete` and the batch worker. Any two of those can
    overlap because they are all dispatched on the thread pool.

    Guard the whole body - the clears, the rebuild AND the update calls - with a
    `threading.RLock` held on the viewer. RLock, not Lock: `delete_rect` calls
    `_update_selections_ui` from inside a handler that may already hold it.

    Create the lock in `__init__`. Never hold it while doing file I/O or OCR.

[C] The batch worker must not rebuild the control tree from its own thread.

    `_run_batch_worker` ends with

        self._switch_image(self.image_src)

    which swaps `image_container.content` and rebuilds every layer, from the
    worker thread, while the user may be dragging. The commander reproduced a
    crash from this independently: with that call blocked, 3 cycles and 47
    interleaved drag/page-turn operations ran clean; with it, the run died on
    operation 6.

    Replace it with a minimal refresh that adopts the cached result for the
    CURRENT page and refreshes the status and the layers under the lock from
    [B], WITHOUT swapping `image_container.content`, WITHOUT reloading the
    image, and WITHOUT touching zoom_scale, offset_x or offset_y. If the current
    page is in `self.pdf_page_map`, there is nothing to adopt.

    The progress callback may keep updating `status_text` and `status_row` - a
    text value and one update is not a tree mutation - but it must not touch the
    layers.

[D] Do not regress the pan feel.

    Panning must still move the image, the rectangles and the highlights
    together, one to one with the mouse. Zoom must still work after panning, and
    `apply_pan` semantics must not change.

[2] `_update_selections_ui` is serialised by an RLock covering mutation AND
