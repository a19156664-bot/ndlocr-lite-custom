## 🎯 プロジェクト目標
- **成果物**: NDLOCR-Lite をベースに、**マウスで矩形範囲を選択してその範囲だけOCRする**デスクトップアプリ
- **第1弾ゴール**: 実用アプリとして一通り（PDF対応・ページ送り・複数矩形・保存・フォルダ一括）
- **方式**: C方式（fork ＋ 追加モジュール）。実装は `custom_gui/` と `tests/` のみ
- **ステータス**: 🟡 進行中

---

## 🧭 設計の前提（2026-07-27 実機検証で確定）

- `src/ocr.py` は1枚あたり約6秒で `.txt` / `.json` / `.xml` を出力する（実測: `resource/digidepo_2531162_0024.jpg`）。
- **`.json` は行単位で `boundingBox`（4隅の "x y" 文字列）・`text`・`confidence`・`isVertical` を持つ。**
- したがって**範囲指定OCRは「全面OCR → boundingBox による矩形内フィルタ」で実現する**ことを基本方針とする。
  部分画像を切り出して再推論する方式は、文脈欠落による精度低下リスクがあるため第1弾では採らない。

### 追加確定事項（2026-07-27 人間承認済み）

1. **1画像内に複数の選択矩形を保持する。**
   矩形は最初から**リスト構造（各矩形が一意のID・ラベルを持つ）**として設計する。
   単一矩形前提で実装してから複数対応へ作り直すことを**禁止**する（Task 04 の時点でリスト構造とすること）。
2. **OCR結果には必ず「元画像のファイル名」をセットで保持・出力する。**
   フォルダ一括処理（Task 12）で結果がどのファイル由来か追跡できることが必須のため、
   Task 02 のデータ構造の時点で `source_image` フィールドを持たせる。
   txt/CSV出力（Task 09）にも画像ファイル名を含めること。

## 📐 OCR 性能に関する実測（2026-07-28・指揮官が計測）

同梱サンプル `resource/digidepo_2531162_0024.jpg`（2048x1446）を2枚処理した実測値。

| 方式 | 所要 |
|---|---|
| `src/ocr.py --sourcedir`（2枚・モデル読込1回） | **52秒** |
| `src/ocr.py --sourceimg` × 2回（モデル読込2回・**現在のアプリの動作**） | **87秒** |

差の35秒＝モデル読込1回分。ここから内訳が確定する。

```
モデル読込  ≈ 35秒   ← 枚数に関係なく1回ぶん
実際のOCR   ≈  8.5秒 ← 画像1枚あたり
```

**現在のアプリは1ページ表示するたびに35秒かけてモデルを読み直している。**
164ページなら約95分がモデル読込に費やされる。一括処理なら35秒で済む。

### 一括処理でも認識品質は変わらない（実証済み）

同一画像を一括／個別で処理し JSON を比較した結果:

```
TEXT IDENTICAL : True     BBOX IDENTICAL : True     CONF IDENTICAL : True
```

唯一の差は `imginfo.img_path` のパス区切り文字のみ。
範囲指定OCRは「全面OCR → 枠内の行を絞り込む」方式のため、
**いつOCRしても結果は同一**である。品質向上を狙うなら解像度や前処理など別の手段が必要。

### OCR結果の保存形式

画像ファイルは画素のみを持ち文字情報を保持できない。
OCR結果は画像と対になる **別ファイル `<画像名>.json`** として出力される（1ページ13.6KB／26行）。
現在は `tempfile.TemporaryDirectory()` に出力して即座に破棄している（ocr_bridge.py）。

※ PDF に限り `--pdf-output` で文字レイヤーを埋め込んだ検索可能PDFを生成できる
  （src/ocr.py の `embed_text_layer_pdf`）。これは成果物であり、アプリの入力形式ではない。

## 🐞 パン中のクラッシュ（2026-07-28）— 根本原因の記録

**症状**: 画像の移動・範囲選択・ページ送りが一斉に不能になる。

```
_on_pan_update → _update_viewer → _update_selections_ui → _safe_update(rects_layer)
AssertionError: assert self.__uid is not None
```

**原因**: flet は非async のイベントハンドラを `page.run_thread` でスレッドプールに
投げており、**直列化しない**（`flet/core/page.py` の `on_event_async`）。
ドラッグ中 `on_pan_update` は毎秒数十回発火し、それぞれ別スレッドで
`_update_selections_ui` が3つのコントロールリストを clear → 再構築 → update する。
flet は uid を `send_commands` の往復後に採番するため、この interleave で
uid 未採番のまま更新され破綻する。`page.update()` のロックは update 同士しか
直列化せず、**更新中のツリー改変は防げない**。

**顕在化の理由**: 競合自体は Task 04/05 から存在。Task 30 のキャッシュにより
全ページが即座にOCR結果を持つようになり、1回のパンで作り直すコントロールが
ゼロ個から数十個に増えて危険区間が伸びた。**Task 30 は引き金であり原因ではない。**

**修正（Task 30c）**:
1. パン時はレイヤーごと移動（`highlight_layer` / `rects_layer` の `left/top` に
   オフセットを持たせ、子は `original_to_display(..., 0, 0)` で配置）
2. `_update_selections_ui` 全体を `threading.RLock` で保護（再入するため RLock）
3. `_run_batch_worker` から `_switch_image` の呼び出しを削除

**効果（4スレッド同時ドラッグ12秒・144行のOCR結果）**:

```
                        修正前    修正後
処理できたパン操作       115回    539回   (4.7倍)
ハイライト残留(正常288)  821個    288個
```

**教訓**: flet でイベントハンドラを書く際は、**常に並行実行され得る**ことを前提に
すること。共有するコントロールリストの再構築は必ず排他すること。
