## 1. マージ

**この箱では、master へのマージと push は [WRITE-I] である。**
AGENTS.md §4 が「実行絶対禁止・人間の明示的承認が必須」と定めている。

**母屋とここが違う。** 母屋は 2026-08-14 に「4つの関門を機械が測ればマージしてよい」へ
改めたが、その判定を行う `merge_if_gates_pass.py` は**この箱には無い**。
**関門を機械が測れない以上、承認者にお願いする形を変えない。**

    統合ブランチ integration/* へのコミット・マージ … [WRITE-R]（自分で行ってよい）
    master へのマージ・git push origin master      … [WRITE-I]（承認をいただく）

**「合格した」と自分で名乗ってマージしない。** 測った結果だけを根拠にする。

承認をいただくときに必ず添えるもの。

    統合ブランチ名と、含まれる Task 番号（破棄したとき何が失われるかが分かるように）
    テスト件数の前後（例：227 → 230）
    抜き取り検査の結果（何本入れて、何本検出したか）
    変更ファイル数と、スコープ外に触れていないこと

## 5. 実機での確認を、承認者にお願いする（飛ばさない）

**これが最後で、最も重要な1項目である。**

この箱は flet のデスクトップGUIで、**画面・カーソル・キー操作はヘッドレスで測れない。**
実測（2026-07-29〜30）。

    テスト 230 本 … 全部緑
    欠陥再注入   … 全部検出
    実機          … Pan のカーソルが手にならなかった（Task 37 → Task 41 で決着）

**見つけたのは、承認者が実機をご覧になったことだった。**

だから、締めの報告には必ず入れる。

    どの画面を
    どの順で押して
    何が見えれば正しいか

**「テストが通りました」で報告を終えない。** それは1行目しか言っていない。

## 6. 終わりの振り返り（指示を待たずに行う）

一連の作業が終わったとき、または「終わりましょう」と言われたときに、毎回 行う。

| 何を | どこへ書くか |
|---|---|
| 効いたやり方 | `.nightly\DEVELOPMENT_LOG.md` の「獲得した知見」 |
| 失敗・再発防止（私の癖なら） | `~\.claude\CLAUDE.md` |
| 失敗・再発防止（この箱の決めごとなら） | `AGENTS.md` |
| 仕様・環境・用語 | `AGENTS.md` |

**新しい置き場を作らない。** 上の4つ以外に書かない。

書き方。

    失敗は「型」で書く（出来事ではなく、次に効く形にする）
    「根拠」を必ず添える（いつ・何が起きたか）
    成功も書く。失敗だけ集めると、やり方が痩せる
